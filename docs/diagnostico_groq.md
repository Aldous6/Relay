El diagnóstico local se ejecuta con `powershell -ExecutionPolicy Bypass -File .\tools\probar_groq.ps1 --diagnose`. Solicita la clave oculta de nuevo, hace una sola llamada al modelo fuerte, no inicia la batería ni reintenta y conserva el resultado en una carpeta nueva `outputs/groq-local/<fecha>/diagnostic.json`. La clave permanece en memoria y se retira al terminar, igual que en el piloto. Los registros anteriores no se alteran.

Un código 500 asignado por LiteLLM no demuestra por sí solo una respuesta HTTP 500 del proveedor. La implementación instalada puede envolver excepciones locales con códigos o tipos de conexión. El adaptador recorre de forma acotada las causas, registra solo clases y códigos numéricos del sistema y separa respuesta HTTP verificable, transporte y contrato local del SDK. Nunca registra mensajes, cabeceras, cuerpos o URLs de esas excepciones. El diagnóstico indica `status_source`; `sdk_reported_unverified` conserva la incertidumbre. Solo se interpreta `http_response` cuando se conserva la excepción HTTP del cliente. Las corridas previas sin esta instrumentación no se reclasifican retrospectivamente.

La prueba de integración offline usa el SDK LiteLLM instalado con HTTP simulado y credenciales ficticias. Comprueba una respuesta 200, un fallo de conexión envuelto por el SDK y una respuesta HTTP 500 sin llamadas adicionales. En LiteLLM 1.109.1, una respuesta simulada sin `service_tier` también reproduce un AttributeError local: se registra como fallo de contrato no reintentable. Esto no establece que esa sea la causa de una corrida real sin su diagnóstico. La confirmación requiere el registro nuevo, no una inferencia a partir de las mismas tareas fallidas.

El modo de diagnóstico captura ahora únicamente error.message de una respuesta estructurada, con la credencial exacta y patrones de claves redactados, sin cabeceras ni failed_generation y con límite de 1000 caracteres. Este texto se conserva solo en diagnostic.json como provider_message_redacted; no forma parte de LiveBackendError.details ni del journal normal. La captura anterior omitía esa explicación y no puede reconstruirla retrospectivamente.

El 12 de noviembre de 2026 se verificó el rechazo `tool_use_failed`: el modo JSON textual recibió «Tool choice is none, but model called a tool». Aclarar el prompt produjo una corrida completa con 1/3 éxitos, sin errores de formato, pero con finales prematuros. El intento posterior con herramientas nativas y `final_answer` requerida produjo otro rechazo: el modelo intentó llamar `commentary`, que no figuraba en el catálogo. Esa corrida quedó interrumpida y se conserva sin convertirla en una evaluación completa.

El adaptador local ahora sigue el flujo de [herramientas locales de Groq](https://console.groq.com/docs/tool-use/local-tool-calling): herramientas declaradas, `tool_choice=auto`, resultados emparejados en mensajes tool y respuesta final textual exacta. No hay herramienta de cierre artificial. Un diagnóstico separado sobre la solicitud antes rechazada recibió una respuesta final válida en 1.535 s; eso verifica ese caso, no sustituye una corrida de tareas. La comparación posterior se guarda en una carpeta nueva, con todas las políticas usando el mismo contrato. Los rechazos explícitos de salida `tool_use_failed` y `json_validate_failed` son semánticos; los fallos de transporte continúan reintentándose con el mismo modelo y límite finito.
